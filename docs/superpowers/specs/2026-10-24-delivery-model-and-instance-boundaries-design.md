# 三种交付方式、实例边界与迁移路径

日期：2026-10-24。依据本轮用户明确的定位修订：全托管服务主要用于试用/业余用户；独立托管实例面向自带服务器的用户，考虑 Serverless 降低控制面成本；开源自部署提供可选付费支持。本文是产品与架构方案，不表示云服务、计费、迁移或 Serverless 已实现。2026-10-26 起基础设施以集群为单位，见 [命名、集群与最小 CLI](2026-10-26-naming-cluster-and-minimal-cli-design.md)。

## 1. 一个产品内核，三种交付方式

| 交付方式 | 目标用户 | 控制面 | 构建/运行资源 | 客户权限与使用 |
|---|---|---|---|---|
| 全托管体验 / Hobby | 没有服务器，先试用或部署业余应用 | 运营方管理 | 运营方提供构建、运行、镜像存储、默认域名和证书 | 用户创建工作空间与应用即可开始；是空间管理员，不是平台全局管理员 |
| 独立托管实例 / Managed | 已有服务器，希望保留控制权并省去控制面运维 | 每客户一套独立实例，由运营方维护；可使用合适的 Serverless 容器平台 | 客户服务器运行 worker 和应用；仓库、默认域名由该全局管理员统一准备，服务方是否代供需在套餐中明确 | 客户拥有本实例完整产品管理权限，可管理多个工作空间；不取得运营方宿主机或其他客户权限 |
| 开源自部署 / Self-hosted | 愿意自行运维、希望完全掌握环境 | 客户自行部署和维护 | 客户自备并管理 | 核心产品保持一致，技术支持按需付费，不自动包含代运维 |

个人账户是与工作空间并列的用户域，Agent 连接与 PAT 属于用户；其授权资源范围可以包含工作空间/应用，不改变归属。自部署实例中的用户身份也不会自动变成运营方跨实例统一账号。

三者共用控制面 + worker、应用模型、API、CLI、MCP 和 Skills，不维护三套代码或三套部署工作流。业务层级始终只有工作空间 → 应用；“实例”是软件部署与管理权限边界，不增加用户业务分组层。

独立控制面可以提高客户之间的隔离，但隔离保证需要包含进程、数据库访问、加密密钥、备份与存储范围，不能仅凭每客户一个容器就宣称全部物理隔离。底层是否共用数据库集群是部署选择，必须与服务承诺一致。

## 2. 基础设施上移到实例级

此前“空间管理员维护执行与镜像策略”的设计在本轮被替代。

- **全局管理员**：集群接入、环境与构建目标、仓库连接与平台凭证、镜像命名规则、应用根域名、证书提供方式、存储类型、配额/套餐策略、工作空间创建、升级与实例恢复。
- **工作空间管理员**：名称、成员身份、空间角色、应用授权概览与应用管理；不能修改实例资源策略或提高平台分配的硬限额。
- **应用维护者/开发者/查看者**：按原有动作权限操作本应用的源码、构建、发布、变量、端口、探针、资源需求、文件/卷与可选自定义域名。

应用根域名属于实例配置（第一版配置在默认环境上），必须与控制台分属不同的可注册域名。用户为应用绑定自己拥有的域名仍是应用能力，需验证归属、DNS 和证书；不能把“用户不能改应用根域名”解释成“用户不能绑定自定义域名”。

第一版每个实例接入一个集群，所有空间共用；以后接入多个集群时，统一配置也不要求所有空间共用同一集群，镜像 repository 则始终按应用分开。平台可以按套餐/隔离策略分配资源，空间只消费分配结果；镜像按实例命名规则和不可变应用 ID 隔离路径。既有部署的集群与历史镜像引用不随默认配置变更自动移动。

模型改为 `InstanceExecutionPolicy`；工作空间的额度/权益与资源分配记录由平台维护，是只读消费关系，不是可编辑的 `WorkspaceExecutionPolicy`。集群、环境与仓库归属实例；构建密钥默认归属应用并在应用内维护，空间共享后续再设计。新建应用仍只填写名称。

## 3. 用户成长与迁移

期望路径：先在全托管环境验证 → 在成本或控制需求变化时迁到自有服务器，继续使用托管控制面 → 需要自己维护整个平台时转为开源自部署。客户也可以直接从任一方式开始。

| 保持一致的部分 | 会发生变化的部分 |
|---|---|
| 工作空间/应用概念、应用页签、构建/发布操作、CLI 命令结构、MCP 工具语义、Skills 流程 | 控制面地址与登录授权、服务器位置、镜像/存储位置、DNS 与证书、运维责任及费用 |

不能承诺三个层面的迁移都是一次无停机点击：

1. **应用迁移**：配置、变量、源码或可验证镜像、应用数据转移到新运行环境，并重新验证健康和访问。
2. **控制面迁移**：工作空间、成员/授权、应用元数据、配置版本、凭证和必要历史按兼容版本导出/恢复；密钥需安全重加密或按支持流程恢复。
3. **数据和访问切换**：PVC/数据库有独立的备份与恢复步骤；平台默认域名不当然随用户迁走，自定义域名由客户控制 DNS。原控制面的 PAT（以及之后的 OAuth 授权）不直接移交给新实例，客户端重新登录或授权。

从第一版开始稳定导出格式与版本号、资源引用和配置模型，避免把宿主绝对路径或特定云提供商 ID 当作应用业务配置。先支持有说明的导出/恢复和迁移演练，再考虑自动化迁移页面。格式稳定不代表永不变化，应提供兼容或升级策略。

用户可以保留使用习惯，迁移成本仍需用真实应用验证。首个演练覆盖一个无状态 HTTP 应用和一个带持久数据的应用，记录手工步骤、停机窗口、凭证重配与失败回退，不用“支持导出”代替迁移成功。

## 4. 竞争意义

这条路径有助于降低第一次接入时的决策成本：先使用，再决定是否购买和维护服务器；增长后可以继续使用熟悉的产品。它也可以使全托管承担体验入口、独立托管承担管理服务订阅、开源承担传播与支持服务入口。以上是商业假设，需要用户与迁移数据验证。

交付方式本身已有竞品覆盖。[Coolify](https://coolify.io/docs/usage)和[Dokploy](https://docs.dokploy.com/docs/core/cloud)都提供托管控制面连接用户服务器与自部署选择；Dokploy 也说明两种方式共享部署引擎。[版本对比](https://docs.dokploy.com/docs/core/differences)

Yummy 应重点验证完整路径的体验：无需服务器即可开始、转自有资源时保持应用模型和 Agent 操作、再转自部署时具备可验证的配置/数据迁移。不能仅凭“提供三种方式”宣称市场独有或自动迁移无成本。

定价入口按用户当前需要组织：直接开始使用 / 连接自己的服务器 / 下载自部署。默认引导试用，不要求第一次访问就理解控制面、registry 或三种架构，也不把每一种方式都分成多排难以比较的技术套餐。

## 5. 全托管收费参考

以下是 2026-10-24 阅读官方网页的快照，后续需重新核对，不作为 Yummy 已确定价格：

| 官方参考 | 当前结构 | 对 Yummy 的启发 |
|---|---|---|
| [Railway 定价](https://railway.com/pricing)、[包含用量说明](https://docs.railway.com/pricing/plans) | Hobby 月最低消费 5 美元、含 5 美元用量；Pro 20 美元、含 20 美元用量；超出部分另计 | 基础月费包含资源额度，避免重复计算；展示预计月费 |
| [Netlify 定价](https://www.netlify.com/pricing/) | Free 每月 300 credits；Personal 每月 9 美元含 1,000 credits；Pro 从每月 20 美元和 3,000 credits 起 | 免费/低价入口配合清楚的额度与加购选项 |
| [Netlify 用量规则](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/) | 计算、带宽、请求、生产发布等转换成 credits，生产发布每次 15 credits | credits 可以统一多种资源，但收费单位应匹配本产品成本与 Agent 使用习惯，不能机械照搬 |

建议的第一步是“试用额度 + Hobby 最低月消费/包含用量 + 用户主动加购”，默认不开启无限超额消费。实际额度与单价等待本机/云上成本实测，不在未选云厂商、未测负载时拍定低价。

计量应围绕成本，而非 Agent 调用次数：

- 构建：先给有限的包含构建额度，记录固定构建规格和实际执行时长；排队不算执行，用户编译失败仍可能消耗算力，平台故障如何返还需明确。
- 运行：初期优先按实例规格和运行时长解释账单；无请求也占用内存的常驻应用不能宣称免费。静态文件托管与常驻容器成本不同，暂不把静态站容器误当成已有 CDN 对象托管。
- 存储与出流量：镜像、持久数据有保留额度，流量有上限或加购；停止运行不自动消除存储成本。
- 发布/回滚：不额外按按钮次数收费；产生的实际资源用量按规则处理。Agent 高频迭代不宜被简单的按发布次数收费阻碍。
- API/MCP/Skills：作为统一使用入口，不因通过 Agent 调用就另收“AI 使用费”；用户自己的模型费用不由本平台重复计收。

试用权益按计费账户/客户限制，不能每创建一个工作空间就无限领取。工作空间可归集用量，硬额度由平台发放，空间管理员不能自行增加。用量台账与发票金额应有独立可追踪事实，不能把缺采样的监控曲线当财务账本。

额度用尽前通知，达到硬限额后停止新增消耗并按公开规则暂停相应工作负载，保留数据恢复窗口；不把系统故障或计量延迟变成无提示删卷。CPU/内存、构建并发/时长、网络和存储上限在接收任务前及运行时共同执行。

## 6. 独立托管与 Serverless

Serverless 是控制面部署手段，不改变实例/工作空间权限边界，也不天然代表每个客户的成本可以归零。现有 Go 控制面包含 worker 双向流、HTTP MCP/SSE、PG 队列扫描、恢复与清理循环以及持久源码/日志；这些是适配验证项。

以 [Cloud Run 长连接文档](https://docs.cloud.google.com/run/docs/triggering/websockets)为参考，流式连接需要处理平台超时与重连；[自动伸缩](https://docs.cloud.google.com/run/docs/about-instance-autoscaling)和[计费/CPU 分配](https://docs.cloud.google.com/run/docs/configuring/billing-settings)说明请求外后台计算与缩至零需要分别设计。此处没有选定 Google Cloud；现有 Connect gRPC/HTTP2 应另做协议验证，不能用 WebSocket 可用来证明 gRPC 一定可用。

先验证合适的容器型 Serverless，允许低规格常驻/最小实例，继续保持每客户单控制面；后续确有收益再适配零实例唤醒。不能只在网页请求时唤醒、却让构建调度和恢复循环在后台永久停住，也不能承诺控制面休眠时仍保持实时监控。已有应用应由用户集群继续运行。

成本要计入持久数据库、Redis、源码/日志存储、备份、网络和实例运维，不仅控制面 CPU。独立实例套餐按控制面托管与支持服务收费，客户自有服务器账单不重复计入平台代供算力费。代供镜像存储/域名或代维客户主机应明确列入服务范围。

当前源码先上传控制面，配置与日志也可能存于托管控制面，因此不能承诺第二种方式“源码与数据从不离开客户服务器”。如未来需要此能力，再设计 worker 直传与相应数据路径。

## 7. 实施边界

先完成可运行的开源内核，用少量独立托管实例验证升级、备份恢复和 Serverless 适配；全托管体验可以小规模限额试运营。开放陌生用户自助执行任意代码前，要完成对应隔离、限额和滥用控制验证，不能沿用可信团队的安全假设。第一种定位为业余用途不会消除这项要求。

OAuth、调度、计费权益校验和管理入口继续作为控制面内模块；执行与采集由 worker 承担，不为三个交付方式另增常驻产品服务。大规模实例编排、专门账务系统和自动化迁移不是本轮实现承诺。

原型已同步三类管理范围：账户菜单进入全局管理，空间菜单进入团队与空间管理，应用列表进入详情（含构建密钥和成员授权）。集群、仓库、应用根域名和执行策略已从空间设置上移；全局/空间审计分开，提供三种身份预览并检查路由与操作权限。原型只有一个示例工作空间，不代表已实现多租户后端、云收费或 Serverless。检查记录见 [QA](../../prototypes/v1-build-console/QA.md)。
