# 创建应用与配置归属复核

2026-10-24 交付模型修订：基础设施由实例管理员统一管理，工作空间不能自定义；以 [交付方式与实例边界](2026-10-24-delivery-model-and-instance-boundaries-design.md) 为准。

日期：2026-10-24。本文修订第一版的创建表单、应用配置和资源策略边界，替代此前“每个应用选择默认节点和仓库”的设计。范围是方案与静态网页原型，未修改正式后端或实现真实调度。2026-10-26 起名称规范、默认地址与运行位置按 [命名、集群与最小 CLI](2026-10-26-naming-cluster-and-minimal-cli-design.md) 修订，下文已同步。

## 1. 结论与取舍

创建应用只需要用户填写 **应用名称**。当前工作空间由所在页面继承，应用 ID、镜像 repository 和默认访问地址由系统生成。创建成功进入本应用的运行配置页，先预览默认值和待确认项；创建不会触发构建、部署或证书申请。

本轮采用“实例管理员统一基础设施，工作空间与应用消费平台能力”。上一轮的工作空间级执行策略已被替代。第一版每个实例一个集群，所有空间共用；以后接入多个集群时，也不开放空间级覆盖。

构建集群、默认环境（运行集群与应用根域名）与输出仓库连接由实例配置；第一版构建和运行在同一个集群。不新增项目或调度配置中心。客户在全托管方式中是空间管理员，在独立托管与自部署方式中可以成为自己实例的实例管理员。

## 2. 字段归属与必填时机

| 信息 | 创建时填写 | 归属及后续操作 | 第一次使用时的要求 |
|---|---|---|---|
| 应用名称 | **唯一必填** | 应用基本信息；空间内唯一，创建后不能修改。命名规范：小写字母、数字和中划线，字母开头，字母或数字结尾，最长 30 位，不能有连续的 `--` | 创建时由后端校验重复与格式；应用 ID 与默认地址后缀由系统生成 |
| 说明 | 不显示 | 应用基本信息，按需补充 | 可空 |
| 工作空间 | 不显示选择器 | 当前上下文，创建后不能靠改配置转移归属 | 请求校验当前空间权限 |
| 应用类型 | 不显示 | 创建后默认 HTTP 服务；配置页可在首次发布前确认 HTTP/后台进程 | 首次部署前确认；后台进程不要求端口、HTTP 探针或域名 |
| HTTP 容器端口 | 不显示 | 应用运行配置，先给 8080 建议值 | HTTP 首发必须确认；不能因为 Dockerfile 有 EXPOSE 就假定实际监听正确 |
| 健康检查 | 不显示 | 应用运行配置，先给 /health 建议值 | HTTP 首发必须确认可用探针；建议值不是已验证事实 |
| 启动命令/参数 | 不显示 | 默认沿用镜像 ENTRYPOINT/CMD，应用高级配置按需覆盖 | 镜像已有启动命令时无需填写 |
| 变量、敏感值、配置文件 | 不显示 | 应用配置；没有用户自定义项时为空，不自动注入不存在的数据库连接 | 仅应用自身确有依赖时必需；平台不把所有应用强制绑定 DATABASE_URL |
| 默认访问地址 | 不填写 | `<应用名>-<6 位后缀>.<应用根域名>`，后缀创建时生成且不变，应用内只读 | 需要公网 HTTP 访问时检查 DNS/HTTPS；未就绪明确显示待处理 |
| 自定义域名 | 不显示 | 应用可选配置；默认地址与自定义域名分开 | 使用自定义域名时验证归属、DNS 与证书 |
| CPU/内存 | 不显示 | 使用平台默认值；应用可在获分配额度内修改运行需求 | 默认值合法即可，无需重复填写 |
| 持久卷 | 不显示 | 默认无卷；应用选择挂载路径与容量，存储类型由管理员统一 | 只有需要持久数据的应用才配置 |
| Dockerfile 路径、构建上下文 | 不显示 | 应用构建设置默认 Dockerfile、.；单次构建可合法覆盖 | 提交构建时必须实际存在并位于源码范围内 |
| 构建参数、目标阶段、构建密钥引用 | 不显示 | 应用/单次构建高级设置 | 可空；只允许引用本应用密钥 |
| 源码归档 | 不显示 | 创建后提交构建时提供，由网页上传或本地 Agent/CLI 打包 | **构建时必需**，创建应用不要求有代码 |
| 构建集群 | **不允许应用配置** | 全局管理 → 集群与执行策略；第一版每个实例一个集群 | 平台按实例策略解析、检查并冻结到任务快照；构建 Job 只调度到通过检查的 amd64 机器 |
| 运行集群与命名空间 | **不允许应用配置** | 由默认环境 prod 绑定的集群决定，命名空间为 `prod-<空间名>`；应用页显示分配结果 | 首次部署受理时冻结到部署记录，之后不因环境改绑或策略修改自动迁移 |
| 镜像仓库地址、前缀、推送/拉取凭证 | **不允许应用配置** | 实例管理员统一配置连接与命名空间 | 构建/拉取前校验；应用 API 不接收推送地址或凭证 |
| repository/tag/digest | **不允许用户填写** | 系统生成或由构建验证，属于产物事实 | 每应用 repository 不同，每构建 tag 不同；不共用 latest |
| 目标架构 | **不允许应用配置** | 首期平台认证范围固定 linux/amd64；实例策略只读显示 | 服务端校验构建机器与产物原生匹配；CLI/MCP 不能绕过 |
| StorageClass、证书提供方式、保留期、并发/配额上限 | **不允许应用配置** | 实例支持边界与实例管理员策略 | 应用只能提出允许范围内的业务需求 |

本轮原型演示名称创建、默认配置预览、类型/端口/探针确认、构建资源只读、平台策略入口。命令覆盖、自定义域名扩展、完整配额和真实能力检查仍按正式实现验收，不能把未画出的字段当作已经实现。

## 3. 创建与第一次发布

```text
应用列表 → 创建应用：名称 → 创建并查看配置
→ 完整应用配置页：待确认运行方式 + 默认值 + 平台托管摘要
→ 保存并确认运行配置 → 上传源码 / 连接 Agent
→ 构建 → 发布 → 运行结果
```

HTTP 默认 8080 和 /health 是可修改建议。配置页明确“尚未部署”，不展示不存在的实例、日志、指标或构建；不把创建成功显示成上线成功。后台类型在首次发布前可改，不需要填写 HTTP 字段。

创建记录不要求资源策略已经就绪：管理员可以先组织应用和授权。构建时缺少集群/仓库会阻止构建，发布时缺少运行能力/入口则阻止发布；提供具体原因和管理员处理入口，不默认选择列表第一项。只构建不要求已确认运行配置；构建并部署必须先确认运行配置。

配置页分为“应用可编辑项”和“平台托管摘要”。后者用文字/只读事实列表解释来源，不放可编辑输入框伪装成应用设置。普通成员看不到平台仓库凭证；空间管理员与应用角色都不能修改实例策略。

## 4. 资源策略与镜像身份

新增 `InstanceExecutionPolicy`（控制面平台管理模块中的数据与逻辑，不新增进程）：包含 policy_revision、build_cluster_id、registry_connection_id、repository_prefix、resource_defaults/limits 等；运行集群与应用根域名由环境（Environment）给出。集群、环境和输出仓库归属实例，控制面负责解析。第一版只有一个集群和默认环境 prod。

`Application` 不存用户可编辑的 cluster_id、registry_id、repository 或 platform 覆盖。应用默认构建参数与运行参数仍分别版本化。首次部署受理时，把集群与命名空间冻结到应用的部署记录（`ApplicationDeployment`，第一版每应用一个 default），它是系统状态，不是应用配置 revision 中可修改的运行目标。即使首发失败也保留，避免重试时因环境改绑集群丢失已创建的本地卷。

镜像路径示例：`ghcr.io/acme-studio/app_<不可变ID>:bld_<构建ID>`，部署使用实际验证的 `@sha256:...`。所有应用使用同一仓库连接与前缀，不等于共用一个 repository。重命名不改变镜像身份；每个 Artifact 保留原仓库、路径、digest 与拉取凭证版本引用。

更换实例策略或环境改绑集群，只影响之后提交的新构建和首次部署，不重写正在执行的任务或历史产物，不迁移现有应用/本地卷，不把旧 release 的镜像地址改写为新仓库地址。旧产物所需仓库连接若仍被引用则不能直接删除；失效时回滚/拉取要给出明确原因。

## 5. API、CLI 与 MCP 一致约束

- `CreateApplication` 的用户输入只有 name 与幂等键；workspace_id 来自路由/上下文，服务端按命名规范校验 name，创建 ID、默认地址后缀、默认部署记录、默认构建配置和未确认运行草稿。创建不顺便建立集群/仓库应用授权关系。
- 空间成员按业务动作权限使用平台分配的执行能力；集群和输出仓库不再维护每应用授权白名单。**构建密钥直接归属应用**，避免把统一资源误解为全部秘密共享。
- 构建预览返回 resolved policy revision、平台、构建集群与镜像路径，只读。`CreateBuild` 再核对预览版本，在事务中固化资源快照；过期返回冲突要求重新预览，不能静默切换。
- 应用修改和单次构建 overrides 只接收允许的业务字段；传入 cluster_id、node、registry、repository、platform 等托管字段明确拒绝。隐藏表单不能替代服务端约束。
- 现有运行应用的发布/重启/回滚使用部署记录中冻结的集群与命名空间；首次部署时按默认环境冻结集群与策略版本。worker 按冻结目标执行，重投不得变成迁移。

## 6. 验收

创建对话框只有一个可填写字段；合法唯一名称创建后进入配置子路由，状态未部署，无构建/实例假数据。创建后可更改类型并确认 HTTP 参数；只构建可独立提交，自动部署在配置未确认时阻止。应用配置及构建提交均没有集群/仓库/架构选择器。平台管理中能看到统一策略来源；新构建记录冻结策略与派发结果，修改策略不移动既有运行实例。网页与 Agent 对托管字段使用同样限制。

原型已同步全局/空间管理分离，并提供对应身份预览与访问拒绝；应用只显示全局配置的只读摘要。原型只使用内存，刷新重置；不交付截图，不连接真实集群。真实事务、能力检查、配额、registry 和权限测试在后端实施阶段完成。

## 7. 构建密钥与应用授权入口修订

此前把构建密钥放工作空间，是预先考虑跨应用复用；第一版没有明确共享需求，因此改为 **默认归属应用、在应用内管理**，不先做空间共享密钥池。

- 平台输出仓库凭证、集群证书等基础设施凭据仍属于全局管理。
- 私有依赖 token、私有模块等构建密钥放“应用 → 配置 → 构建设置”，仅当前应用可引用。运行时密码继续放应用变量，不能把两种生命周期混用。
- 构建密钥只有名称、用途、版本与已配置状态可读；新建/替换时输入值，保存后不返回已有明文。构建任务绑定应用自己的密钥 ID 与版本，不接收其他应用的密钥引用。
- “应用 → 配置 → 成员与权限”是本应用授权的主要入口。工作空间成员页保留授权概览与跳转，读取同一份 `application_members` 数据，不再提供一套平行授权表单。
- 空间层负责邀请/移除空间成员、修改空间角色；应用页授予/收回具体应用角色。第一版仍由空间管理员修改应用访问授权，移动入口不会自动赋予应用开发者或维护者授权他人的能力。应用维护者可管理本应用业务配置与构建密钥。
- 应用授权对象必须已经是当前空间的有效成员；不能在应用内新增全局用户、提升空间/全局权限，或移除空间管理员对应用的继承访问权。移除应用访问不等于移除空间成员。

这是资源归属与使用位置的简化，不新增进程。空间共享密钥若出现明确需求，再单独设计共享范围与轮换行为；第一版不显示共享入口。
