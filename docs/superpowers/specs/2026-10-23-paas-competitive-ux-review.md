# Yummy 第一版竞品与体验复评

日期：2026-10-23。范围：用户提供的 Railway 截图、竞品官方文档、当前产品/技术方案和本地交互原型。没有登录竞品进行完整可用性测试，也没有验证 Yummy 后端、集群或真实 MCP 客户端。

## 1. 判断

当前功能范围可以作为第一版研发基线，已经覆盖可信团队自托管应用的主要闭环：源码上传、构建、部署、HTTPS、变量/配置、日志、基础监控和版本恢复。正式发布仍需要实现和验证这些能力，原型不能作为产品已可用的证据。

竞争重点应是“Agent 能可靠完成部署并解释结果”。Go、k3s、MCP 本身不足以证明体验或商业优势；成熟竞品也有 API/CLI、监控和运维能力。Yummy 应通过同一场景验证价值：开发者完成代码后，由 Agent 准备 Dockerfile、确认上传内容和发布计划，服务器构建 AMD64 镜像，返回真实可访问地址；失败时指出阶段、错误证据与下一步，重试不会重复执行。

现在不需要再扩展业务层级或增加页面数量。优先解决首次成功、变更可理解、失败可恢复三个问题。

## 2. 竞品能力与取舍

以下比较来自官方文档，描述产品能力参考，不是功能覆盖率评分。

| 参考与已记录能力 | 对 Yummy 的意义 | 第一版取舍 |
|---|---|---|
| [Railway 暂存更改](https://docs.railway.com/deployments/staged-changes)：检查差异、应用更改、丢弃更改 | 用户要知道保存的内容何时进入线上，能在发布前核对 | 保留草稿/生效版本；增加应用内差异预览、统一确认、放弃全部更改。逐项放弃后续补充 |
| [Railway 变量](https://docs.railway.com/variables)：变量编辑、批量编辑与 sealed variables | 敏感变量不应通过详情或 diff 泄露；普通变量需要方便维护 | 普通值可读、敏感值只替换；导入预览；发布 diff 显示敏感值已替换 |
| [Coolify 应用配置](https://coolify.io/docs/applications/configuration/overview)：按任务分组配置、健康、资源、域名等 | 成熟度来自具体任务组织，不能把全部配置堆成一张无边界表单 | 一级保持七个应用页签；配置内分运行/构建，再按入口、健康、资源、文件、存储分段 |
| [Coolify 首次应用](https://coolify.io/docs/applications/)与[CLI 部署](https://coolify.io/docs/cli/deploy-applications)：先验证服务器，再完成部署与排错 | Agent 接入不能替代基础设施就绪与首个成功部署 | 管理员完成节点、仓库和入口检查；普通成员只处理已授权应用。首个应用提供明确下一步 |
| [Dokploy 应用](https://docs.dokploy.com/docs/core/applications)：部署之外还有变量、域名、日志与监控 | 构建成功只是中间步骤，日常维护是用户使用价值的一部分 | 当前已纳入首期完整范围，不能重新退回“只做构建” |
| [Dokploy 监控](https://docs.dokploy.com/docs/core/monitoring)、[通知](https://docs.dokploy.com/docs/core/overview)和[平台备份](https://docs.dokploy.com/docs/core/backups) | 自托管长期使用还涉及异常发现与平台恢复 | 首期必须有可执行的备份恢复说明与演练；复杂告警后置，基础发布失败通知作为试用反馈后的优先项 |

Railway 的拓扑适合多服务依赖关系。Yummy 当前应用为单容器，第一版采用应用卡片和独立详情更直接；不添加没有真实依赖数据的画布。

## 3. 界面评审与本次调整

### 3.1 已有设计值得保留

- 工作空间 → 应用两层清晰，日常界面没有基础设施管理侧栏。
- 完整应用页集中部署、构建、日志、监控、变量和配置，深链接保持上下文。
- 当前运行状态与最近构建结果分开，构建失败不会让用户误以为线上已经停止。

### 3.2 主要问题

| 优先级 | 原有问题与影响 | 本次处理 |
|---|---|---|
| P0 | 草稿只显示版本号；点击部署时看不到实际差异 | 原型增加变量、端口、健康、资源、域名、配置文件与卷的差异摘要；显示当前/待部署版本；确认时固定所审查版本 |
| P1 | 大量 9～12 px 字号与偏淡灰绿文字，状态、正文、辅助信息相似 | 改为中性浅色、深色主操作、蓝色链接/焦点；正文 14 px，辅助 13 px，徽标 12 px；成功/警告/失败保留语义色 |
| P1 | 应用标题区域留白过多，主内容靠下 | 顶栏由 72 px 缩至 64 px，减少标题区垂直留白，桌面内容宽度保持有限上限 |
| P1 | Agent 接入只藏在账户菜单，与当前应用关联较弱 | 应用标题增加“连接 Agent”；有预置远程授权示例的应用自动带入选择，其余应用明确展示本地接入说明 |
| P1 | 变量错误只弹 toast，不知道哪个字段需要修改 | 增加就地错误、无障碍关联与错误字段聚焦，保留输入 |

视觉检查：原先偏淡配色、大段留白和微小文字削弱了真实控制台感；本次保留必要留白与表格结构，去除通篇绿色。继续避免装饰性 KPI、空图表、没有业务数据的拓扑和未实现的 AI 对话入口。界面的辨识度主要来自清楚的发布状态与操作反馈。

### 3.3 明确的视觉方向

第一版只提供中性浅色。使用语义变量区分背景、表面、文本、辅助文本、分隔线、主操作、链接、焦点和状态；日志可使用深色阅读面。后续双主题通过同一组 token 映射实现，届时再增加主题选择和跟随系统选项，本版不显示不可用主题入口。

正式实现映射 Tailwind CSS 4 + shadcn/ui 的 CSS 变量体系，React/TanStack 技术选择不变。字体优先系统无衬线，中文使用系统中文字体；ID、路径、命令与日志使用等宽字体，不依赖外部字体网络请求。

## 4. 仍需要补齐的产品交互

这些是研发验收项，除明确写为“原型已有”的内容外，不表示本次全部实现。

| 场景 | 第一版验收要求 | 当前状态 |
|---|---|---|
| 管理员首次使用 | 创建空间后按节点 → 仓库 → 入口 → 应用完成检查；每个失败项有诊断和重试，不需要先研究完整管理导航 | 原型有接入指引与诊断示例，实际检查未实现 |
| 创建首个应用 | 输入名称、类型、资源与 HTTP 端口后创建真实应用；进入未部署空状态，提供上传/Agent 接入下一步；后台进程不要求域名 | 2026-10-24 已补充名称创建、内存保存与配置页跳转；未部署应用不显示假实例/指标，真实持久化待实现 |
| 发布前检查 | 检查有效节点、仓库权限、镜像架构、端口、探针、资源与配置版本；域名/TLS 单独显示待处理，提供原因 | 技术方案有边界，原型主要展示阶段；真实预检待实现 |
| 变更发布 | 已保存更改可核对/放弃；新发布固定 image digest + 配置版本；检查后发生并发更改需重新确认 | 原型已有差异、放弃全部、版本检查；后端需原子比较版本 |
| 表单离开 | 区分未保存输入、已保存待发布、已发布；只对会丢失的输入提示，已保存草稿可自由切页 | 变量对话框保留输入；运行设置离开保护待正式实现 |
| 发布/回滚失败 | 保留阶段日志、错误证据、旧版运行状态和再次尝试入口；镜像被清理或配置不可用时阻止回滚 | 原型有成功/失败场景，真实恢复与依赖校验待实现 |
| 日志与监控 | 时间范围、发布/实例上下文、采集时间、缺测、数据上限和断线恢复可理解；时间轴单位明确 | 原型有示例、过滤和缺测；真实分页、游标、Tooltip 等待成熟组件实现 |
| 生命周期 | 归档停止新操作；删除应用与删除持久数据分开；说明引用与保留规则，危险操作再次确认 | 方案范围已有部分定义，归档/删除页面尚未演示 |
| 自托管恢复 | 说明 PG、源码/日志目录、加密主密钥、CA、集群与卷数据分别如何备份；在新实例完成恢复演练 | 已有备份说明要求，恢复脚本/演练尚未实现；不是仅写一句“请自行备份” |

不把托管数据库、多服务拓扑、通用 CMDB、APM 或规则引擎加入这一轮。基础失败通知值得优先观察：试用者是否因为没有及时知道发布失败而受阻；如需要，可从控制面内的简单 Webhook 投递与重试做起，无需新进程或先建通知平台。

## 5. Agent First 的验证标准

人工和 Agent 使用同一应用权限、配置版本、构建、发布与操作记录。网页用于了解状态和审核变更；CLI/MCP 返回可继续处理的结构化结果。

- 上传前显示所属空间/应用、包含与排除的文件、Dockerfile/上下文、大小与目标架构；本地已有代码不要求用户先制作 OCI 镜像。
- 计划与执行分开。发布计划包含镜像来源、配置版本、差异、预计中断和验证步骤；Agent 不能依靠自然语言“成功”替代操作状态。
- 所有写操作有幂等键和持久 operation ID，连接断开后可恢复查询；重试不重复发布。
- 失败返回稳定错误码、发生阶段、日志/事件引用与可执行下一步。系统仅在有明确证据时描述原因，不把推测当诊断结论。
- 发布完成返回 release、运行版本、健康与访问验证结果、地址和日志链接；后台进程返回就绪状态，不伪造 HTTP URL。
- Skills 描述准备 Dockerfile、排除密钥、预览配置、部署和验证的流程；工具继续负责实际鉴权、校验和执行。需要通过真实客户端完成一次完整任务测试。

## 6. Skill 校核

已使用本地 `ui-ux-pro-max` 检索设计系统、Web 表单验证和 shadcn 表单/焦点建议。设计系统检索两次分别返回文档站/营销落地页模式，与运维控制台不匹配，因此没有保存其自动生成的整套设计系统，也没有采用其深色默认或营销标题字体。保留已确认的中性浅色、应用详情结构和系统字体。

验证相关结果明确匹配 Web 的字段错误关联、可聚焦错误摘要，以及 shadcn/TanStack Form 的 Field/FieldError 适配；正式实现采用这些成熟组件，当前原型仍使用原生 dialog。图标沿用既定 Lucide，不套用该 Skill 针对原生 App 的图标与安全区规则。

## 7. 发布前的通过标准

1. 非作者能在不口头指导的情况下完成首个 HTTP 应用，从本地目录到真实 HTTPS 地址；记录完成时间、卡点与人工补救次数，先建立实测基线，不编造效率提升比例。
2. 修改变量后线上保持不变；差异确认后发布生效；放弃草稿不影响实例；敏感明文不会出现在页面/API diff/日志中。
3. 故意构建失败、健康失败、节点离线和证书未就绪，用户能区分当前运行状态与操作结果，并找到下一步。
4. 375 / 768 / 1024 / 1440 px、键盘路径与 200% 缩放可用；主要操作和文字清晰，表格/日志局部滚动；无整页横向溢出。
5. 完成控制面/worker 重启恢复、权限拒绝、幂等重试、备份恢复与保留策略验证，再宣称第一版可用。
