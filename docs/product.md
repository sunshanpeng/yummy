# Yummy 产品文档

Yummy 面向需要把本地源码部署到自有或受托管集群的开发者和可信团队。一次交付从源码上传开始，经过构建并验证镜像、部署、就绪与入口探测，最后交付可访问的应用和可查询的发布记录。使用者可在应用内继续管理配置、查看日志和资源趋势、启停及恢复发布。

## 1. 交付方式与首期范围

| 交付方式 | 实例和权限边界 |
| --- | --- |
| 全托管体验 | 平台维护实例和运行基础设施，客户作为空间管理员管理成员与应用 |
| 独立托管 | 客户提供服务器或集群，运维方维护独立实例，客户可拥有该实例的全局管理权限 |
| 开源自部署 | 自行运行同一套控制面、worker 和客户端，自主管理数据、入口、仓库与升级 |

三种方式共用一套产品能力。全托管的商业供应、计费和服务承诺另行定义。首期每实例使用一个 k3s 集群与默认环境 `prod`，每应用一个默认部署 `default`、一个运行副本。应用类型包括单容器 HTTP 服务、静态站点和后台进程。后台进程不建立业务 HTTP 入口。应用可以通过运行变量连接外部数据库。

## 2. 资源、名称与访问地址

- 业务层级为工作空间 → 应用。构建、镜像产物、运行配置版本、发布、日志和指标都属于应用。环境和部署描述运行位置。
- 空间标识和应用名由小写字母、数字及单个中划线组成，字母开头，字母或数字结尾，最多 30 字符。标识与应用名创建后固定，空间另有可修改的显示名称。
- 创建应用只填写应用名，创建后进入配置页。系统生成固定的六位地址后缀，默认地址为 `<应用名>-<六位后缀>.<应用根域名>`。应用根域名与控制台属于不同的可注册域名。
- 平台管理集群、环境、输出仓库、仓库前缀、应用根域名与执行策略。应用继承平台策略，首次实际部署固定运行位置，之后的平台变更不会移动运行资源。
- HTTP 应用可声明自定义域名。域名解析、入口证书和 TLS Secret 由安装方配置。发布与持续探测分别展示应用就绪、域名和 HTTPS 状态。

## 3. 账户、角色与管理入口

| 入口 | 可访问者及职责 |
| --- | --- |
| 个人账户 | 每位登录用户管理自己的访问令牌与 Agent 连接。选择授权时可指定目标空间和应用 |
| 全局管理 | 全局管理员管理用户、工作空间、集群、节点与机器、环境、仓库、域名与策略，并查看全局审计 |
| 工作空间管理 | 空间管理员修改空间资料、邀请与维护成员、管理空间角色与应用授权、查看空间审计 |
| 应用详情 | 按应用授权查看概览、部署、构建、基本信息或进入成员与权限。空间管理员在这里维护应用授权 |

空间管理员继承本空间应用的业务管理能力，最后一位空间管理员不能被移除或降级。普通空间成员需要显式应用授权。应用管理员可维护构建/运行配置、构建密钥与运行启停。开发者可以上传源码、构建、发布、回滚及重启。查看者可浏览已授权应用的构建、产物、运行日志及基础监控。已有敏感值不提供读取明文；应用授权仍由空间管理员维护。操作的最终许可取决于服务端校验和用户当前有效身份。

网页支持账号密码登录。安装方启用团队 OIDC 后，可为现有账号绑定身份提供方的 subject；空间资格仍由 Yummy 管理。CLI 支持个人 PAT，也可在启用 OAuth 时通过浏览器授权。远程 MCP 使用 OAuth，连接地址绑定一个应用；令牌的实际权限受当前用户授权、目标应用和令牌 scope 共同约束，用户可以撤销自己的凭证或连接。

## 4. 从源码到应用

全局管理的「接入检查」根据平台策略、节点资格、仓库验证、空间分配和应用运行情况显示准备进度。根域名配置后，入口检查仍需等待实际 HTTP 应用通过探测。

1. 全局管理员登记执行节点，确认其构建、运行与入口资格，准备输出仓库及应用根域名。空间管理员创建应用、授予访问权限并确认应用运行设置。可先创建应用，再准备集群与实例策略。
2. 从本地项目目录运行 `yummy use <空间名>/<应用名>`，以 `yummy deploy --dry-run` 检查项目文件、构建方式和目标。CLI 负责本地打包、上传；网页可上传符合规则的 `.tar.gz`，或使用已上传的快照；远程 MCP 可用已有快照提交构建。
3. 设置了 Dockerfile 路径时验证并使用它；未设置时优先使用选定上下文根目录的 Dockerfile；默认文件缺失时由 Railpack 识别源码。显式路径错误或 Dockerfile 构建失败直接展示原错误。源码归档排除敏感文件并拒绝越界路径、符号链接和特殊文件。
4. 提交时可以选择只构建，或构建成功后自动发布。自动发布绑定提交时的运行配置与运行版本条件，相关条件改变时会返回冲突。CLI 可等待结果，也可用 `--no-wait` 返回构建 ID、由控制面继续处理。
5. 构建成功可复制验证过的镜像 digest。页面分别展示构建进度、最近发布结果、当前运行版本与访问状态。取消构建会等待执行确认；失联时显示恢复或未知状态。重新构建创建新记录，原日志继续关联原构建；源码保留期届满后需重新上传。

网页按空间的应用列表组织日常工作。每个应用有独立详情页面，构建记录、日志、配置、部署和监控在应用内查看。CLI 与远程 MCP 提供结构化标识、状态、错误及分页数据，命令和接入参数见 [身份接入](operations.md#身份接入)。

## 5. 配置、发布与恢复

| 操作 | 生效方式 |
| --- | --- |
| 保存配置 | 生成运行配置版本，页面提示未部署更改。支持类型、端口、启动参数、探针、资源、变量、配置文件、自定义域名及卷配置 |
| 部署更改 / 重新部署 | 使用已验证镜像和选定配置创建发布，复用镜像的操作无需重新构建源码 |
| 回滚 | 先核对目标镜像和配置差异，再用历史发布的镜像和配置新建发布，保留尚未生效的设置及卷数据 |
| 重启 / 停止 / 启动 | 由 worker 执行。停止后的持久卷继续保留，启动恢复最近适用的运行版本 |
| 归档 | 空间管理员在已停止运行且无在途发布后归档。应用退出日常列表，名称、卷和历史仍保留 |
| 删除 | 空间管理员从「已归档应用」发起。无集群执行历史的应用可直接释放名称；有执行历史的应用在构建结束后由 worker 核验归属、清理资源 |
| 删除持久卷 | 工作负载清理后若还有卷，需输入应用名单独确认。控制面收到清理完成结果后释放名称。底层数据由存储类的回收策略处理，历史和审计继续关联原应用 ID |

发布记录、应用当前提供服务的版本及最近的实际观察分别展示。失败的发布保留原因与事件；若旧版本仍在提供服务，界面继续显示旧版本。worker 失联时以最后观察时间作为判断依据。回滚与停止不回退外部数据库或持久卷中的数据。

归档空间前需归档全部应用，并完成已经受理的清理任务，确保管理员仍可确认删卷或重试。

## 6. 日志、监控与运维

- 构建日志独立于运行日志。运行日志来自应用容器的 stdout/stderr，可按 Pod、容器、时间和发布版本读取。控制台与 CLI 支持跟随。应用停止后，控制台仍可查询保留的日志。不同容器实例的日志交错显示时，控制台分别解码。页面文本查找限定于已加载结果。升级前采集且没有版本信息的日志可在不按版本筛选时查询。
- 运行监控包含就绪、重启与异常事件、入口探测、CPU 和内存趋势。首个 CPU 样本不足、离线、停止和缺测分别显示，曲线缺口不补零。HTTP 探测延迟描述平台探测结果。
- 应用日志和指标均有保留边界，详见 [数据保留](operations.md#5-运行配置与数据保留)。构建、发布、授权和资源操作保留审计。外部仓库的镜像淘汰策略及应用数据备份由实例运维方管理。
- 迁移实例需要单独处理数据库、源码、密钥、镜像、域名、卷和授权。安装、升级、数据恢复和实机验收记录见 [运维手册](operations.md)。

## 7. 后续范围与验收

Git 自动部署、预览环境、多容器、多副本、多架构、多个环境和跨集群迁移、托管数据库、复杂告警、通用 APM、商业计量、SCIM 和自动跨实例迁移均属后续范围。控制面按需缩至零还需验证 worker 长连接、后台任务与持久存储。首期的源码执行面向可信用户和团队。

验收以可验证的结果为准。对照 [技术验证清单](technical.md#8-测试与实机验收) 检查本地源码预览、构建、真实 HTTPS、日志、指标、回滚、空间隔离和数据保留。历史验证与当前仍待实机验证的项目见 [运维验收记录](operations.md#7-验证状态与限制)。早期交互可查看 [静态原型](prototypes/v1-build-console/index.html)，其中的数据为演示数据。
